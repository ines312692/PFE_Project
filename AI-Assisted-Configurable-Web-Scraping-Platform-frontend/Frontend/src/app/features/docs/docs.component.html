Welcome to ElyaScrape

AI-assisted web scraping platform: configurable jobs, anti-bot bypass, schema-driven extraction, and multi-format export.

ElyaScrape is a configurable, AI-assisted web scraping platform. Define targets, configure extraction schemas, and let the platform handle rendering, anti-bot evasion, retries, and data cleaning automatically.

What is ElyaScrape?

ElyaScrape lets you create scraping jobs through a web interface without writing code. Each job targets one or more URLs, defines what data to extract, and runs on a schedule or on demand.

The platform automatically selects the right browser engine based on the target site's protection level Playwright for standard sites, Selenium with stealth mode for Cloudflare-protected ones.

You never choose between Playwright and Selenium. The platform probes the target site and selects the engine automatically before each run.

Getting started

Authentication

ElyaScrape secures every request with JWT access tokens and refresh tokens. The web client authenticates through a Backend-for-Frontend (BFF) token layer.

Signing in

New users register from the /register page; existing users sign in from /login. After a successful login the backend issues a short-lived access token and a longer-lived refresh token. The frontend never stores raw tokens in JavaScript memory the BFF layer manages them through secure cookies.

The auth interceptor automatically attaches the session and silently refreshes the access token when it expires you don't need to handle token renewal manually.

OAuth sign-in

In addition to email and password, ElyaScrape supports OAuth2 providers. The provider redirects back to the /callback route, which exchanges the authorization code for a session through the BFF token service.

Roles & access

Access is controlled with role-based permissions (RBAC). Routes are protected by the auth guard and the role guard, so each user only sees the features their role allows.

Role Can do
ADMIN Full access manage users, proxies, audit logs, and all projects.
OPERATOR Create and run jobs, configure schemas, manage their own projects.
VIEWER Read-only access to dashboards, results, and job history.

Project-level roles

On top of the global account role, each project carries its own membership. When you invite someone to a project, you assign them a project role that scopes what they can do inside that project only, independent of their account-wide role.

Role names above reflect the UserRole and ProjectRole enums. Adjust the labels here if your enum values differ.

Core concepts

Jobs & pipelines

A job is the core unit of work in ElyaScrape. It bundles a target, an extraction schema, browser settings, and a schedule into one runnable configuration.

Anatomy of a job

Every job belongs to a project and is built from a few configuration blocks. You set them up once in the job creation wizard, then reuse or duplicate the job as needed.

Block Purpose
Target The starting URL (or list of URLs) to scrape.
Extraction schema The fields to extract and the mode used (CSS, XPath, LLM, regex).
Browser config JS rendering, stealth mode, delays, timeouts, user agent.
Crawler config Crawl depth, page limits, URL include/exclude patterns, pagination.
Retry policy How failed requests are retried before the job is marked failed.
Schedule Manual, cron-based, or webhook-triggered execution.

Job lifecycle

A job moves through a controlled set of states. Every transition is recorded so you can audit exactly when a job ran and what happened.

State Meaning
CREATED Configured but not yet scheduled or run.
QUEUED Waiting for an available worker.
RUNNING Actively scraping pages.
PAUSED Temporarily suspended; can be resumed.
WAITING_FOR_HUMAN Paused on a CAPTCHA or challenge that needs manual intervention.
COMPLETED Finished successfully results are available.
FAILED Stopped after exhausting the retry policy.

Priority

Each job carries a priority (LOW, NORMAL, HIGH) that determines how it is ordered in the worker queue when several jobs are waiting at once.

Dry-run / test mode

Before committing to a full run, you can execute a job against a limited sample of pages. The dry run applies your full extraction schema and returns a preview, so you can confirm the configuration is correct without spending a full crawl budget.

Use templates to skip configuration. Saving a job as a template lets you spin up new jobs for similar sites in seconds see the job templates library.

Core concepts

Scraper vs Crawler

ElyaScrape supports two job types. The right choice depends on whether you already know the URLs you want, or you need the platform to discover them for you.

Scraper

Targets a known URL or an explicit list of URLs. The platform fetches each page, applies your extraction schema, and returns structured data. No link discovery best when you know exactly what to extract.

Crawler

Starts from a seed URL and follows internal links using a URL frontier. It handles pagination, depth limits, and include/exclude filters automatically best for collecting many pages from one site.

When to use a Scraper

Choose a Scraper job when you have a fixed set of pages product detail pages, a list of article URLs, or a single dashboard. Extraction runs once per URL with no navigation overhead.

When to use a Crawler

Choose a Crawler job when the pages you want are not known in advance. The crawler discovers links from the seed page, deduplicates URLs, respects robots.txt, and walks paginations (numbered, infinite scroll, or "load more").

Both job types share the same extraction schema, browser config, and ETL pipeline only the navigation behaviour differs.

Core concepts

Extraction modes

ElyaScrape offers four extraction modes. You pick one per schema in the visual schema builder, and you can combine approaches within a single job.

The four modes

Mode How it works Best for
CSS_SELECTOR Maps each field to a CSS selector. Well-structured pages
XPATH Maps each field to an XPath expression. Deep or irregular DOM paths
LLM You describe the data in plain language; an LLM returns structured JSON. Unstructured or variable markup
REGEX Pattern matching applied to the raw HTML or text. Simple, repetitive patterns

Picking a mode

Use CSS or XPath when the page has a stable structure and you want fast, deterministic extraction. Switch to LLM mode when the layout varies from page to page or there are no reliable selectors. Regex is a lightweight option for values embedded in raw text.

When a CSS or XPath selector breaks after a site layout change, the AI selector healer detects the rupture and proposes a corrected selector automatically.

The schema builder

All modes are configured through the visual schema builder, which provides a dedicated panel per mode a fields editor for CSS/XPath, a regex editor, and a prompt-driven panel for LLM extraction with a built-in prompt assistant.

Core concepts

Browser engine

ElyaScrape uses two browser engines internally Playwright and Selenium. The selection is automatic and transparent.

Automatic engine selection

Before each job run, the platform probes the target URL and detects anti-bot signals:

Detected signal Engine Stealth
None Playwright User setting
CLOUDFLARE Selenium Forced ON
DATADOME Selenium Forced ON
AKAMAI Selenium Forced ON
LIKELY_BLOCKED Selenium Forced ON
When Selenium is auto-selected, stealth mode is always forced ON regardless of user configuration. Scraping Cloudflare without stealth would fail systematically.

JS Rendering vs Stealth Mode

These two toggles solve different problems:

JS Rendering

Launches a real browser to execute JavaScript. Required for SPAs (React, Angular, Vue) where content is rendered client-side. Without it, the platform fetches raw HTML fast but incomplete for dynamic pages.

Stealth Mode

Injects scripts that hide browser automation signals: masks navigator.webdriver, randomises canvas fingerprint, injects fake plugins. Prevents detection even when JS Rendering is enabled.

Human behaviour simulation

On top of stealth patches, the engine can mimic human interaction generated mouse paths, variable scrolling, and typing rhythm so that behaviour-based detection systems see realistic activity rather than instant, mechanical actions.

Crawling & site analysis

Site analysis

Before a job runs, ElyaScrape probes the target site to detect protections, estimate difficulty, and recommend the right scraping strategy.

The site probe

The site probe inspects the target URL and produces a diagnostic report. It detects which anti-bot vendor is in front of the site, whether JavaScript rendering is required, how pagination behaves, and how the DOM is structured all before a single page of data is scraped.

Detected protections

Dedicated detectors run against the response to identify the protection layer in place:

Detector Identifies
CLOUDFLARE Cloudflare IUAM, Turnstile, WAF, JS challenges.
DATADOME DataDome device-fingerprint protection.
AKAMAI Akamai Bot Manager.
PERIMETERX PerimeterX / HUMAN bot defence.
CAPTCHA hCaptcha, reCAPTCHA, and similar challenge widgets.

Scraping difficulty score

The probe combines several factors detected protections, required JS rendering, pagination complexity, and DOM structure into a single difficulty score. The score is surfaced as an easy / medium / hard rating so you know what to expect before committing resources.

Factor Effect on score
Anti-bot protection Strongest driver Cloudflare or DataDome push the score toward "hard".
JavaScript rendering Client-rendered SPAs raise difficulty over static HTML.
Pagination Infinite scroll and "load more" are harder than numbered pages.
DOM structure Irregular or unstable markup increases difficulty.

Origin IP discovery

For sites hidden behind a CDN, the probe can look up historical DNS records to find a candidate origin IP. Where validated, this lets the platform reach the origin server directly and sidestep the edge protection layer.

The probe also reads robots.txt. If the target pages are disallowed, you'll see an alert before the job starts see the Crawling page for how rules are enforced.

Crawling & site analysis

Crawling

A Crawler job discovers pages by following links from a seed URL, managing a URL frontier, deduplicating links, and respecting site rules along the way.

The URL frontier

Crawling is driven by a URL frontier the queue of URLs still to visit. Each discovered link becomes a crawl node carrying its depth and parent. The frontier feeds the pipeline one node at a time, applying depth and page limits as it goes.

Link discovery & normalisation

As each page is fetched, links are harvested, normalised to a canonical form, and filtered against your include/exclude patterns. Normalisation prevents the same page from being visited twice under slightly different URLs (trailing slashes, query order, fragments).

Crawler control Purpose
Max pages Hard cap on how many pages the crawl visits.
Max depth How many link-hops from the seed the crawl is allowed to go.
Include patterns Only URLs matching these patterns are followed.
Exclude patterns URLs matching these are skipped entirely.

Sitemap seeding & file discovery

The crawler can seed the frontier from a site's sitemap to reach pages faster, and can discover linked files (documents, feeds) encountered during navigation.

robots.txt compliance

A robots gate reads the site's robots.txt and, by default, skips disallowed paths. Crawl-delay and rate guidance are honoured so the crawl stays polite toward the target server.

Pagination is handled as part of crawling but configured separately see the Pagination page for the detection strategies.

Crawling & site analysis

Pagination

ElyaScrape detects and walks paginated listings automatically, whether they use numbered pages, infinite scroll, or a "load more" button.

Pagination strategies

A registry of strategies is tried against the page; the one that matches drives navigation through the result set.

Strategy Handles
NUMBERED Classic page-number links (1, 2, 3 …).
NEXT_BUTTON A "next" link or arrow advancing one page at a time.
LOAD_MORE A button that appends more results in place.
INFINITE_SCROLL Content that loads as the page is scrolled.
URL_PARAM Page driven by a query parameter (e.g. ?page=2).
AUTO Let the platform detect the right strategy automatically.

Automatic detection

In AUTO mode, the platform samples the page markup and infers the pagination type. When the structure is ambiguous, an LLM-assisted detector inspects the sample and proposes the most likely strategy.

SPA hydration

Single-page applications often load their list content after an initial hydration step. A hydration analyzer waits for client-side rendering to settle before pagination is evaluated, so dynamically injected items aren't missed.

Infinite scroll and "load more" require JS rendering to be enabled they depend on a real browser to trigger the additional loads.

Anti-bot & stealth

Anti-bot & stealth

Progressive anti-bot strategy that automatically escalates based on the site's resistance level.

Delay margin

The requestDelayMs field is a margin, not a fixed delay. The actual inter-request delay is randomised:

Formula 
actual_delay = 500ms + random(0, requestDelayMs)

Example: requestDelayMs = 2000
→ actual delay between 500ms and 2500ms per request

This breaks the fixed-interval pattern that anti-bot systems use to detect automated scraping.

Stealth patches applied

Patch What it does
navigator.webdriver Set to undefined instead of true
Canvas fingerprint XOR applied to first pixel on every toDataURL() call
Plugins list Fake Chrome PDF Plugin injected
Languages Set to ['fr-FR', 'fr', 'en-US', 'en']
Launch args --disable-blink-features=AutomationControlled

Human behaviour simulation

Beyond static fingerprint patches, the platform can simulate human interaction generated mouse paths along bezier curves, natural scrolling, and variable typing rhythm. This defeats behavioural detection that looks for instant, perfectly mechanical actions.

Stealth, proxies, and CAPTCHA solving are layered. The platform applies the lightest measure that works and escalates only when a site resists.

Anti-bot & stealth

Proxy rotation

For sites that block by IP, ElyaScrape routes requests through a managed pool of health-checked proxies, rotated by a configurable strategy.

Rotation strategies

Strategy Behaviour
ROUND_ROBIN Cycles through proxies in order.
RANDOM Picks a proxy at random for each request.
FASTEST Prefers the proxy with the lowest measured latency.
LEAST_USED Spreads load by picking the least-used proxy.

The proxy pool

Proxies are gathered from multiple sources and registered in a managed pool. Each proxy carries metadata protocol, anonymity level, country, and current status that the rotation strategies use when selecting one.

Health checking

A background health checker continuously tests proxies and records their outcome. Failing proxies are taken out of rotation automatically, so jobs only run through endpoints that are currently responsive.

Geo-targeting

Proxies can be filtered by country to access geo-restricted content. A strict-geo option ensures requests only go out through proxies in the requested region.

Per-proxy anti-bot status

The platform tracks how each proxy fares against specific protections such as Cloudflare and DataDome, so it can prefer proxies that are known to pass a given site's defences.

The proxy dashboard (admin) shows pool health, country distribution, and anti-bot pass rates at a glance.

Anti-bot & stealth

CAPTCHA solving

When a site presents a challenge, ElyaScrape detects the CAPTCHA type and routes it to a solver. Difficult cases can fall back to a human.

Supported challenge types

Type Notes
reCAPTCHA v2 image grids and v3 score-based detection.
hCaptcha Image selection and drag challenges.
Turnstile Cloudflare's challenge widget.
FunCaptcha Rotation-based challenges.
GeeTest Slider and image-analysis challenges.

The solver pipeline

Detection runs first to recognise that a challenge is present and which family it belongs to. The challenge is then handed to a solver registry, which selects an appropriate solver. Solved tokens are cached and re-injected so the same challenge doesn't have to be solved twice in a session.

Solver options

The architecture is plugin-based. Challenges can be solved by an external CAPTCHA service, by an LLM-vision solver for image challenges, or by a mock solver in testing. New solvers can be added without touching the orchestration layer.

Human intervention

When automated solving isn't possible, the job transitions to WAITING_FOR_HUMAN and surfaces the challenge for manual completion. Once a human solves it, the job resumes from where it paused.

Solving CAPTCHAs may have legal and terms-of-service implications. Use this feature responsibly and review the target site's policy first.

Configuration

Retry policy

When a request fails, ElyaScrape retries it according to a configurable policy before marking the job as failed.

RetryPolicy fields

Field Type Description
maxRetries integer Number of retry attempts after the first failure.
backoffMultiplier number Factor the delay is multiplied by on each successive attempt.
baseDelayMs integer Starting delay before the first retry.
jitterMs integer Random extra delay added to each retry to avoid synchronised retries.

Exponential backoff

Delays grow exponentially with each attempt, plus a random jitter:

Formula 
delay(attempt) = baseDelayMs * (backoffMultiplier ^ attempt) + random(0, jitterMs)

Example: baseDelayMs=1000, backoffMultiplier=2, jitterMs=500
attempt 1 → 1000-1500ms
attempt 2 → 2000-2500ms
attempt 3 → 4000-4500ms

Circuit breaker

On top of retries, a per-domain circuit breaker tracks the error rate. If a domain keeps failing, the breaker opens and temporarily stops requests to that domain, then re-enables it progressively. This protects both your job and the target server.

Field names above mirror the RetryPolicy model adjust them here if your implementation uses different names.

Extraction schemas

A schema declares what data a job extracts. It is a list of typed fields, each bound to a selector or described in natural language.

Structure

An ExtractionSchema has an extraction mode and a list of fields. Each field has a name, a data type, and the rule used to locate its value.

Example schema 
{
  "mode": "CSS_SELECTOR",
  "fields": [
    { "name": "title",   "type": "STRING",  "selector": "h1.product-title", "required": true  },
    { "name": "price",   "type": "NUMBER",  "selector": "span.price",       "required": true  },
    { "name": "inStock", "type": "BOOLEAN", "selector": ".availability",    "required": false }
  ]
}

Field types

Type Description
STRING Plain text value.
NUMBER Numeric value parsed and normalised.
BOOLEAN True/false, derived from presence or text.
DATE Date value, normalised to ISO 8601.
URL Absolute or resolved link.
LIST Repeated values matched by the same selector.
The type list reflects the SchemaFieldType enum. Update this table to match the exact values your enum defines.

Schema presets

For common use cases e-commerce, listings, news the schema builder ships ready-made presets so you don't start from scratch.

Schema validation

Before a schema is saved, a validator service checks it for consistency missing field names, invalid selectors, type mismatches and surfaces issues so you can fix them up front rather than discovering them mid-run.

CSS / XPath selectors

The developer-oriented extraction modes. Bind each schema field to a precise selector with the integrated editor.

Concise and readable. Ideal for class- and id-based targeting, e.g. div.product > span.price. The fastest option for well-structured pages.

Prefer stable, semantic selectors (ids, data attributes) over deep positional paths they survive layout changes far better.

Data pipeline

Selector auto-healing

When a CSS or XPath selector stops matching after a site changes its layout, the platform detects the break and proposes a corrected selector automatically.

Why selectors break

Selectors are tied to a page's structure. When a site is redesigned class names change, elements move, wrappers are added a previously reliable selector can suddenly return nothing. Without healing, the job would silently produce empty fields or fail outright.

How healing works

When an expected field comes back empty, the selector healer takes the current DOM and the field's description and asks an LLM to locate the most likely replacement element. It returns a candidate selector that maps back to the field you originally defined.

1

Detect the break

A required field returns no value while the page loaded successfully.

2

Analyse the DOM

The healer samples the current markup and reasons about where the field's value now lives.

3

Propose a fix

A corrected selector is suggested so extraction can continue.

Healing is also surfaced by the site structure-change monitoring, which can alert you proactively when a layout shift threatens your existing selectors.

Data pipeline

LLM extraction

Describe the data you want in plain language. A language model reads the page and returns structured JSON no selectors required.

How it works

In LLM mode you write a short prompt such as "extract every product name and its price". The platform samples the page HTML, sends it to the model, and parses the response back into your schema fields. This works even on pages with irregular markup where CSS and XPath would be brittle.

Prompt example 
Extract all job listings from this page.
For each one return: job title, company, location, and salary.
Return null for any field that is missing.

Prompt assistant

The schema builder includes a prompt assistant that helps you refine your description, suggests fields, and previews the structured output before you commit the schema.

Prompt injection protection

Because page content is fed to a model, malicious pages could try to hijack the prompt. ElyaScrape runs a security guard that sanitises sampled HTML and blocks instruction-injection attempts before the content reaches the model.

LLM mode is the most flexible but also the slowest and most costly per page. For high-volume jobs on stable sites, prefer CSS or XPath.

Data versioning

Every run's output is stored as a version, so you can track how a dataset evolves, compare runs, and roll back when something goes wrong.

Why version your data

Scraped sites change. A run today may return different records than last week new products, updated prices, removed listings. Versioning keeps a history of each run so changes are observable rather than silently overwritten.

What a version captures

Captured Why it matters
Run output The full set of records produced by that run.
Timestamp When the version was created, for chronological tracking.
Quality report Completeness and consistency metrics attached to the version.

Comparing versions

You can diff two versions of the same job's output to see exactly what changed which records were added, removed, or modified. This is the foundation for change-monitoring use cases such as price tracking or catalogue monitoring.

Rollback

If a run produces bad data after a site change broke a selector, for example you can roll back to a previous version while you fix the configuration.

Version diffs pair naturally with notifications you can be alerted when a new version differs significantly from the last.

API reference

Webhooks

Webhooks let ElyaScrape react to external events and notify other systems when scraping data is ready.

Two roles

Inbound

An external system calls a webhook URL to trigger a job. Useful for event-driven scraping run a job whenever an upstream change happens.

Outbound

ElyaScrape calls your endpoint when a job finishes, delivering the result or a status update as a JSON payload.

Signature verification

Each webhook is issued credentials and every outbound delivery is signed. Your receiver should verify the signature to confirm the payload genuinely came from ElyaScrape and was not tampered with.

Delivery status

Outbound deliveries track a status so you can see whether a notification was sent, succeeded, or failed and needs a retry.

Status Meaning
PENDING Queued, not yet sent.
DELIVERED Receiver responded successfully.
FAILED Delivery failed after retries.
Status values mirror the WebhookDeliveryStatus enum adjust them to match your exact definitions.

Error codes

When a request fails, ElyaScrape returns a structured error so you can react programmatically.

Error response shape

Error response 
{
  "success": false,
  "data": null,
  "error": {
    "code": "JOB_NOT_FOUND",
    "message": "No job found with the given id",
    "subErrors": []
  }
}

Error categories

Errors fall into two families. Domain errors describe a business rule violation (the request was understood but rejected). Infrastructure errors describe a technical failure split into client-side 4xx and server-side 5xx.

Category HTTP range Meaning
Domain error 400 / 409 Validation or business rule violation.
Infrastructure 4xx 401 / 403 / 404 Auth, permission, or missing resource.
Infrastructure 5xx 500 / 503 Unexpected failure or unavailable dependency.
